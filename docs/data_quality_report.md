# Отчёт о качестве данных

## 1. Контекст и входные данные

В лабораторной работе используется набор данных **Seoul Bike Sharing Demand**, содержащий почасовые сведения о количестве арендованных велосипедов в Сеуле, календарных и погодных условиях.

Аналитический вопрос: определить, как почасовое количество арендованных велосипедов различается в зависимости от времени, календарных и погодных условий.

Одна строка исходного набора соответствует одному часу работы системы велопроката Seoul Bike.

В качестве бизнес-ключа используется сочетание полей `Date + Hour`: для одной календарной даты каждый час должен встречаться не более одного раза.

Исходный файл читается непосредственно из слоя `raw` SeaweedFS:

```text
s3://raw/seoul_bike_sharing_demand/ingested_on=2026-10-13/SeoulBikeData.csv
```

Исходный объект в процессе лабораторной работы не изменялся.

Исходный набор содержит **8760 строк**, соответствующих полному годовому набору почасовых наблюдений.

1. Дубликаты по бизнес-ключу `Date + Hour` и пропуски в ключевых аналитических полях отсутствуют. Это позволяет использовать почасовые наблюдения без дополнительного восстановления ключевых значений.
2. Диапазоны `Hour`, `Rented Bike Count` и `Humidity(%)` соответствуют принятым ограничениям. Явных структурных проблем в выбранных полях при профилировании не обнаружено.

Предупреждающие правила также не выявили нарушений, поэтому quality-флаги в подготовленном наборе имеют значение `false`.

## 4. Подготовленные данные

В результате обработки сформированы два Parquet-файла:

```text
s3://staging/seoul_bike_sharing_demand/source_ingested_on=2026-10-13/staging.parquet
```

```text
s3://staging/seoul_bike_sharing_demand/source_ingested_on=2026-10-13/quarantine.parquet
```

Баланс строк:

```text
raw        = 8760
staging    = 8760
quarantine = 0

8760 = 8760 + 0
```

В `staging.parquet` нормализованы имена аналитических полей. Например:

- `Rented Bike Count` → `rented_bike_count`;
- `Temperature(°C)` → `temperature_c`;
- `Humidity(%)` → `humidity_pct`;
- `Wind speed (m/s)` → `wind_speed_ms`;
- `Seasons` → `season`;
- `Functioning Day` → `functioning_day`.

Также добавлены поле `source_ingested_on` и два признака качества:

- `quality_flag_invalid_humidity`;
- `quality_flag_functioning_day_inconsistent`.

Поскольку предупреждающих нарушений не обнаружено, оба признака имеют значение `false`.

`quarantine.parquet` создан даже при отсутствии исключённых записей и содержит определённую схему, включая поля `quality_rule_ids` и `quarantine_reason`.

После сохранения `staging.parquet` был повторно прочитан непосредственно из SeaweedFS. Повторная проверка показала:

- дубликатов `date + hour` — 0;
- пропусков `rented_bike_count` — 0;
- недопустимых значений `hour` — 0;
- отрицательных значений `rented_bike_count` — 0;
- установленных warning-флагов — 0.

Количество строк не изменилось, дополнительные объекты и дубликаты в SeaweedFS не появились. Следовательно, обработка воспроизводима при одинаковых входных данных, параметрах и правилах качества.

Основные ограничения дальнейшего анализа:

1. Данные относятся только к Сеулу и охватывают один годовой период с декабря 2017 года по ноябрь 2018 года, поэтому результаты нельзя без дополнительной проверки переносить на другие города или современные условия.
2. Данные агрегированы по часам и не содержат идентификаторов отдельных поездок, пользователей или станций. Поэтому по ним нельзя анализировать маршруты конкретных поездок или спрос на уровне отдельных станций.
